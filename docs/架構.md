## 資料流

### Modbus Flow（採集 → MQTT → Web）

```
Modbus TCP Devices
    ↓ FC01/02/03/04 polling（自有 ModbusTcpTransport：TID 比對收框；多 ID 單站失敗不斷 TCP → 功能說明書_Engine核心.md §4.7）
ScadaEngine.Engine / ModbusCommunicationService
    ↓ raw value × Ratio → engineering value, quality = Good/Bad
MqttPublishService  (Topic: SCADA/Realtime/{coordinatorName}/{SID}, QoS=1, Retain=true)
    ↓
MQTT Broker (127.0.0.1:1883, no auth)
    ↓ subscribe SCADA/Realtime/+/+
ScadaEngine.Web / MqttRealtimeSubscriberService
    ↓ ConcurrentDictionary<SID, RealtimeDataItemModel>
RealtimeController → /RealTime page
```

Engine 同時寫 SQL Server：`HistoryData`（時序）與 `LatestData`（upsert）。

> **外部系統 / 第三方訂閱 MQTT 整合手冊** → [對外整合_MQTT即時資料訂閱.md](對外整合_MQTT即時資料訂閱.md)（Broker 連線、Topic、Payload JSON schema、Python / Node.js / C# 範例）

### DB 來源 Flow（外部寫入 → Engine polling → SCADA pipeline）

```
外部系統（PLC / 第三方 / 手動匯入）
    ↓ INSERT/UPDATE WHERE SID='DB1-S5' （Value 直接寫工程值）
DBLatestData  (SID, Value, Timestamp, Quality) — 統一入口表
    ↓ polling (per Coordinator PollingInterval, CommandTimeout=ConnectTimeout)：SELECT WHERE SID LIKE 'DB1-%'
DbCommunicationService (Engine BackgroundService)
    ├─ HistoryData：所有已配置 row 餵 HistoryDataStorageService（分鐘 dedup + 60s Timer），Timestamp = polling 當下時間（與 Modbus 一致）
    │   讀失敗（HasEverReadSuccessfully=true 後）→ 對全部 SID 寫 Quality=Bad、Value=LastSeen 最近成功值
    └─ 變化偵測（值/品質/DBLatestData.Timestamp 任一不同才繼續，僅擋下游噪音通道）
        ↓ UPSERT LatestData (Timestamp = DBLatestData.Timestamp)
        ↓ publish MQTT SCADA/Realtime/{Name}/{SID} → 後續警報 / 計算點 / 能源報表 / Web 即時數據
```

SID 命名 `DB{CoordinatorId}-S{Sequence}`（不與 `{ModbusID}-S{N}` 或 `CALC-S{N}` 撞號）；Sequence 由載入器以 JSON 陣列索引+1 自動產生（與 Modbus 對齊，JSON 不顯式指定），每個 Coordinator 上限 100 點。設定由 Web「DB 來源」頁**匯入 Excel**（`DB來源範本.xlsx`，一張工作表 = 一個 Coordinator；預覽差異 → 確認 → Web 寫 `DBPoint/{SheetName}.json` 並自動發 `SCADA/Sys/DbCoordinator/Reload`，Retain=false），JSON 仍是 Engine 的執行期唯一設定來源：Engine 啟動／Reload 讀全部 JSON、UPSERT by Name 到 DBCoordinator/DBPoints、重建 polling loops。Modbus 來源同樣走 Web 匯入 Excel（`Modbus範本.xlsx`，靠 watcher 生效；刪除 = JSON 移到 `_deleted/`、Engine 收 Deleted 停採集），兩者共用 `ScadaEngine.Web/Services/SourceExcel/` 框架（adapter 分來源）。**Excel 中加新點位一律加最後一行**，中間插入會位移後續 SID（匯入預覽會標示「SID 位移」並要求另外勾選確認）。詳見 [功能說明書_DB來源管理.md](功能說明書_DB來源管理.md)。

> **HistoryData.Timestamp 的取捨**：DB 來源的 HistoryData.Timestamp 用 polling 當下時間（不抄 DBLatestData.Timestamp），與 Modbus 行為一致 — 外部停寫時 HistoryData 仍每分鐘一筆，trending / 用電報表時間軸不斷。LatestData / Realtime / MQTT 的 Timestamp 仍用 DBLatestData.Timestamp 反映外部寫入真實時間。

> **內建 Weather Coordinator（氣象資料來源）**：`DBPoint/Weather.json`（S1=外氣溫度、S2=外氣相對濕度）的「外部系統」是 **Web 端 `WeatherFetchService`** — 依 `/WeatherSetting` 頁設定（CWA 授權碼、測站、間隔）週期呼叫中央氣象署開放資料 API 寫 DBLatestData（Timestamp=觀測時間；API 失敗或觀測 >60 分過舊 → Quality=0）。詳見 [功能說明書_氣象資料來源.md](功能說明書_氣象資料來源.md)。

### OPC UA 來源 Flow（OPC UA Client polling → SCADA pipeline，Web 全欄位動態編輯）

```
外部 OPC UA Server (opc.tcp://..., 帳密驗證, SecurityPolicy None)
    ↓ Session + RegisterNodes；週期批次 Read（依 Server OperationLimits.MaxNodesPerRead 分塊、對齊 Device 邊界）
OpcUaCommunicationService (Engine BackgroundService，每 Server 一條 polling loop)
    ├─ HistoryData：全部點位每輪餵 HistoryDataStorageService（分鐘 dedup）；連線/讀取失敗 → Quality=Bad、Value=最近成功值
    └─ 變化偵測（值/品質變化 或 3 分鐘定期重發，比照 Modbus STALE 防護）
        ↓ UPSERT LatestData → UpdatePersistentCacheOnly → publish MQTT SCADA/Realtime/{Name}/{SID}
        ↓ AlarmMonitorService.EvaluateBatchAsync → CalculatedPointService.CalculateAndPublish
控制寫回：SCADA/Control/{SID} → MqttControlSubscribeService（cid 前綴 OPC 分流）
    ↓ OpcUaCommunicationService.WriteNodeAsync — AO 寫入原始值 = 輸入值 ÷ Ratio、DO 寫 bool；唯讀點位（ControlType 空）拒絕
```

SID 命名 `OPC{CoordinatorId}-S{Seq}`。與 DB 來源最大差異：**設定可在 Web「OPC UA 來源」頁全欄位動態編輯（含新增/刪除 Server、Device、點位），免重啟 Engine**。`OpcUaPoint/{Name}.json` 是 source of truth（一檔一 Server，內含 Devices 分組，點位數不設上限），Web 存檔時：驗證 → 回寫 JSON → UPSERT `OpcUaCoordinator`/`OpcUaPoints`（DB 為執行期快照）→ 發 `SCADA/Sys/OpcUaCoordinator/Reload`（Retain=false）→ Engine `OpcUaReloadSubscriber` 收到後 `ReloadAsync()` 重讀 JSON、重建 Session/polling loops。`Seq` 由 Web 配號並持久化於 JSON（`NextSeq` 單調遞增、刪除不回收）— SID 被 HistoryData/警報/計算點位引用，插入/刪除點位不可位移其他點位 SID。亦可在同頁以 **Excel 範本／匯出／匯入**批次維護（`OPCUA範本.xlsx`，一張工作表 = 一個 Server、Device 欄分組；點位**以 Seq 欄比對**而非位置，刪中間列／重排／插入都不漂移，無 Seq 的列以 NodeId 對回既有點位；匯出不含密碼、空白 = 保留；提交後 Web 依 JSON UPSERT DB 再 reload；不產生刪除候選）。三種來源的網頁熱編輯都在 JSON 記 `WebEditedAt`、匯出 Excel 記 `ScadaExportedAt`，拿舊 Excel 重匯會警告「會蓋掉網頁修改」並要求另外勾選（JSON 是唯一真相、Excel 只是檢視）。「匯出 Excel」直接寫進各來源的 `WatchedFolder`（固定檔名覆寫留 `.bak`；Engine watcher 只看 `*.json` 不受影響），可從資料夾直接匯入，熱編輯／匯入／刪除後自動重產資料夾內受影響的 xlsx（Excel 開著或有未匯入修改則不覆寫並提示）— 規則見 [功能說明書_Modbus來源管理.md](功能說明書_Modbus來源管理.md) §4.1。Web 寫檔路徑由 `appsettings.json` 的 `EngineOpcUaConfig`（`WatchedFolder` = Engine 實際讀取的部署資料夾 + 可選 `MirrorFolder` 鏡像寫回 repo）明定，原子寫檔（tmp → `File.Replace` → 留 .bak），與 Modbus 熱編輯線的 `EngineModbusConfig` 同慣例。詳見 [功能說明書_OPCUA通訊.md](功能說明書_OPCUA通訊.md)。

### Modbus Server Gateway（對外供值分支 — 第三方用 Modbus TCP 讀本系統即時值）

```
MQTT SCADA/Realtime/+/+ ────────────▶ ┌─ ScadaEngine.ModbusServer（獨立進程/獨立安裝）──┐
LatestData（啟動預填）─────────────▶ │ RealtimeCache（SID→值，複製 Web 訂閱模式）       │
DBLatestData（DB 來源點位輪詢）────▶ │   ↓ 每秒掃寫（word order 編碼 / 品質不良→NaN）   │
                                      │ FluentModbus TcpServer :502  ← 第三方 FC4 讀取    │
                                      │ Kestrel 瀏覽網頁 :5041       ← 位址對照表         │
                                      └───────────────────────────────────────────────────┘
```

四類點位（Modbus / 計算 / DB / OPC UA）分段配置 Modbus 位址（float32 × 2 registers、**append-only 持久化於 `AddressMap.json`** — 位址一經配定永不重排/回收，下游 PLC/HMI 位址表永久有效）。訂閱 DbCoordinator / OpcUaCoordinator Reload 主題自動重掃。與 Engine/Web 完全解耦：只引用 Common、`InstallModbusServer.bat` 獨立安裝（不在主 Install.bat 範圍）、服務名 `JoularisModbusGateway`。詳見 [功能說明書_ModbusServerGateway.md](功能說明書_ModbusServerGateway.md)。

## 資料庫結構初始化與欄位同步

`ScadaEngine.Engine/DatabaseSchema/DatabaseSchema.json` 是**建表 + 欄位的唯一真相來源**。加欄位只改此檔，不再手寫遷移碼。

**執行者**：Engine（`DataServiceExtensions.InitializeDatabaseAsync`）與 Web（`Program.cs` 啟動時）都跑同一個 `DatabaseInitializationService.InitializeDatabaseSchemaAsync` — 消滅部署順序依賴，誰先重啟誰補。Web 端失敗僅 log 不擋啟動（DB 連不上時例外被服務內部攔截、回傳 false）。

**啟動流程**（`DatabaseInitializationService`）：

```
1. 建缺的表        — 逐表查 INFORMATION_SCHEMA.TABLES，缺 → CREATE TABLE（含 PK / 叢集索引）
2. 改名遷移        — MigrateColumnsAsync：僅手寫 sp_rename 段（schema diff 無法推斷改名，看起來像「刪A加B」）
                     必須先於欄位同步，否則新名會被補成空欄位、舊資料孤兒化
3. 欄位同步        — SyncMissingColumnsAsync：逐表比對 INFORMATION_SCHEMA.COLUMNS vs schema
                     缺欄位 → ALTER TABLE ADD（用 schema 的型別/NULL/Default 定義）
```

**同步原則 — 只加不減不改**（生產 DB 零風險；唯一例外是可證明無損的字元欄位加寬）：

| 情境 | 行為 |
|------|------|
| schema 有、DB 缺 | 自動 `ALTER TABLE ADD`，log info |
| DB 有、schema 沒有（人工加過的欄位） | 不動，log warning（漂移可見） |
| 型別不一致 | 不改，log warning（漂移可見） |
| Nullability 不一致 | 不改，log warning（NULL→NOT NULL 需先處理既有 NULL 值，是資料決策） |
| 字元欄位**純加寬**（同型別+同 nullability，如 nvarchar(100)→(500)/MAX） | 自動 `ALTER COLUMN`（無損 metadata 操作），log info；受 PK/索引/約束相依擋下時 log warning 請人工加寬 |
| 字元欄位縮短（DB 比 schema 寬） | 不改，log warning（截斷風險） |
| 缺的欄位是 IDENTITY / PK | 跳過（無法事後 ADD），log error 要求人工遷移 |
| 缺的欄位 NOT NULL 且無 Default | 跳過（對非空表 ALTER 必失敗），log error 要求 schema 補 Default |
| 單欄 ALTER 失敗（Engine/Web 同時啟動 race） | log warning 不中斷整批，另一端已補上即正確 |

機制冪等：欄位齊全時整段無任何 ALTER；未解決的漂移每次啟動持續警告（可見性）。

## 資料庫自動建立與每週備份

核心原則：**安裝時特權與執行時權限分離** — 高權限動作（CREATE DATABASE、建 login、資料夾 ACL）收斂到一次性 `Setting/install-db.ps1`（安裝人員 Windows 帳號 + SSPI，不碰 sa）；日常運行只用 dbSetting.json 的低權限帳號（db_owner）。

`install-db.ps1` 已綁入部署流程自動執行：現場 `Install.bat`（BuildRelease.ps1 產出，步驟 [5/8]、在還原現場設定後）與開發機 `DeployService.ps1` install/update（`Invoke-DbSetup`，QuickDeploy.bat 選項 1/6 都會經過）。失敗不中斷部署，印警告與手動重跑指令。

> 打包產物結構、現場資料夾（Modbus/DBPoint/OpcUaPoint 都只帶 `*.xlsx` 空白範本）、升級時設定的備份/還原對照 → 見 [功能說明書_Release打包與升級.md](功能說明書_Release打包與升級.md)。

**自動建 DB 安全網**（`DatabaseInitializationService.EnsureDatabaseExistsAsync`，Engine/Web 共用，掛在建表流程最前）：

```
1. 直接開目標 DB    — 成功即返回（既有環境零負擔）
2. 連 master 查 DB_ID — DB 存在但開不了 → log 權限指引，返回 false
3. DB 不存在 → CREATE DATABASE 於 DbMaintenanceSetting.DataFileFolder + RECOVERY SIMPLE
   ├─ 路徑/ACL 失敗 → 退 SQL Server 預設路徑重試（仍設 SIMPLE），log 警告
   └─ 無 CREATE DATABASE 權限（SqlError 262）→ log「執行 install-db.ps1 或請 DBA 建立」，返回 false
```

既有 DB 完全不動（含復原模式）。新建 DB 一律明確設 `RECOVERY SIMPLE` — 避免繼承 model 的 FULL 導致交易記錄檔無限成長。

**每週自動備份**（`DatabaseBackupService`，Engine BackgroundService）：

- 排程讀 `Setting/DbMaintenanceSetting.json`（預設週日 03:00），主迴圈每 30 秒檢查，同 EnergyLeafAggregationService 模式；失敗當日內每小時重試
- 純 T-SQL `BACKUP DATABASE`，**不依賴 SQL Agent**（Express 無 Agent），db_owner 權限即可
- A/B 兩檔輪替（`{db}_A.bak` / `{db}_B.bak`，`WITH INIT` 覆寫較舊者）— 恆保留本次 + 上一次，磁碟用量可預測
- 壓縮依版本自動判斷：`SERVERPROPERTY('EngineEdition')` 為 2 (Standard) / 3 (Enterprise) 加 `WITH COMPRESSION`，4 (Express) 略過
- 結果寫 EventLog（EventType=3、SID=`_system`；成功 Severity=3、失敗 Severity=2），Web 事件紀錄頁可見
- 啟動自檢：備份資料夾缺失或最新備份逾 8 天 → log 警告，不靜默失敗

**檔案 I/O 歸屬**：CREATE DATABASE 的 MDF/LDF 與 BACKUP 的 .bak 都由 **SQL Server 服務進程**寫入，資料夾需授權 SQL 服務帳號（`NT Service\MSSQLSERVER` 或 `NT Service\MSSQL$實例名`）— 這是 install-db.ps1 的職責之一。DB 在遠端主機時 `TO DISK` 路徑指的是 DB 那台的磁碟。

備份與 DB 檔同機同碟只防「DB 損毀」、防不了磁碟故障 — Backup 資料夾應定期外拷。詳見 [docs/功能說明書_資料庫自動建立與備份.md](功能說明書_資料庫自動建立與備份.md)。

## 共用設定檔解析順序

「這台機器連哪個 SQL Server」「這台機器用哪個 SMTP / 簡訊盒 / Line token」都是**機器層級的事實**，一台機器只有一個答案，所以這些設定檔不屬於任何一個 app：生產機放在 **`C:\JOULARIS\Shared\`**，Engine / Web（dbSetting 另含 ModbusServer Gateway）都讀這一份。以前各 app 各帶一份、靠打包時複製維持一致，升級時又各自備份／還原，一旦分家就永久分家（2026-10-06 現場 Engine 與 Web 指向不同 DB 即因此）；通知三檔更糟 —— Web UI 的 SMTP / 簡訊設定頁**會寫檔**，以前寫進 Web 複本，Engine 永遠看不到。

| 檔案 | 讀 | 寫 | 環境變數層 | 改後生效 |
|---|---|---|---|---|
| `dbSetting.json` | Engine / Web / Gateway | 手動（或 install-db.ps1） | `JOULARIS_DBSETTING` | 重啟 |
| `EmailSetting.json` | Engine（寄信）/ Web（測試寄送、能源日報） | Web「警報設定 → Email」SMTP 設定 | 無 | Web 存檔 → MQTT 熱重載（見下） |
| `SmsSetting.json` | Engine（發簡訊）/ Web（throttle 秒數） | Web「警報設定 → 簡訊」簡訊盒設定 | 無 | Web 存檔 → MQTT 熱重載 + 重掃序列埠 |
| `LineSetting.json` | Engine（推播）/ Web（測試發送） | 手動（含 token，不進 git） | 無 | Engine：重啟或發 Reload；Web：下次測試發送自動重讀 |

所有 app 都呼叫 `ScadaEngine.Common` 的 **`SharedSettingLocator.Resolve(檔名[, 環境變數名])`**（[SharedSettingLocator.cs](../ScadaEngine.Common/Data/Services/SharedSettingLocator.cs)；`DbSettingLocator` 是它帶環境變數層的薄包裝），同一套順序、第一個存在的檔勝出：

| 層 | 路徑 | 情境 |
|----|------|------|
| 1 | 環境變數（絕對路徑）— **僅 dbSetting 有此層** | 明確覆寫：測試、多實例。設了但檔不存在 → 略過往下找 |
| 2 | `<BaseDirectory>\..\..\Shared\<檔名>` | 生產機：`C:\JOULARIS\<App>\App\` 往上兩層 = `C:\JOULARIS\Shared\`，各 app 算出同一個檔 |
| 3 | `<BaseDirectory>\Setting\<檔名>` | 單機獨立安裝（例：Gateway 裝在另一台機器，找不到 Shared）/ 舊佈局 |
| 4 | `<CWD>\..\ScadaEngine.Engine\Setting\<檔名>`，找不到再從 BaseDirectory 逐層往上找 `<祖先>\ScadaEngine.Engine\Setting\<檔名>` | 開發模式：各專案 `dotnet run` / F5 都讀 repo 內 Engine 那份，不依賴 CWD（ModbusServer 啟動會把 CWD 切到 BaseDirectory） |

- **第 2 層刻意排在第 3 層之前**：共用檔存在就一定贏過本機複本，杜絕 stale 複本被優先讀到；因此生產機 `<App>\App\Setting\` 下**不留**四檔複本（Install.bat 會刪），Engine csproj 也以 `<None Remove>` 不讓它們進 build 輸出（開發 bin 若有舊殘留要手動清，否則第 3 層會先命中）
- **Web 寫入位置 = 解析到的那一份**（讀寫同一條路徑）；四層都不存在時退到 Shared（Shared 資料夾存在）否則開發 repo，並 log warning —— 以前都不存在會寫到 CWD 相對路徑，服務模式下 CWD 是 system32，等於寫到不知名角落
- 程式碼不出現 `C:\JOULARIS`，全靠 BaseDirectory 相對推算；找不到時 `DatabaseConfigService` 退回內建預設、通知三檔視為未設定（該通道停用），都 warning 列出搜尋過的路徑
- 各 app 啟動 log 印 **`資料庫設定檔路徑: <絕對路徑>（來源: …）`** 與三行 **`通知設定檔路徑: <絕對路徑>（來源: Shared / 本機 Setting / 開發 repo）`** — 排查「Web 改了 Engine 沒生效」先比 Engine 與 Web 的這幾行是否同一路徑。Web 的 Serilog 在 appsettings 無 `Serilog` 區段時預設：服務模式寫 `Log\Web-.log`、開發模式印 Console（與 Engine / Gateway 同模式）
- **通知三檔熱重載**：Web 存檔成功後發 MQTT `SCADA/Sys/Notify/Reload`（`{"file":"EmailSetting.json","requestId":"…"}`），Engine `NotifySettingReloadSubscriber` → `NotifySettingReloader` 重讀同一份檔、呼叫對應服務既有的 `InitializeAsync`（簡訊走 `ReloadSettingAsync` → `ISmsTransport.ReloadAsync` 關舊 port 重掃，不開第二個佇列 worker）；成功 / 失敗都寫 EventLog（EventType=3，SID=`_system`）並回 `SCADA/Sys/Notify/Status`（帶 requestId），Web 存檔請求等最多 8 秒把結果顯示給使用者（已套用 / Engine 未回應 / 套用失敗）。**JSON 壞掉或套用丟例外 → 保留舊設定**，載入失敗根本不呼叫服務；Engine 離線時指令丟失，但下次啟動本就讀 Shared 新檔，結果一致。不必重啟 Engine，採集 / 控制 / 警報不中斷
- `install-db.ps1` / `reset-engineer-password.ps1` 以同精神找檔（環境變數 → Shared → 同資料夾／舊佈局），不走 .NET 的 Locator
- `DbMaintenanceSetting.json`、`MqttSetting.json`、`DatabaseSchema.json`、Modbus / DBPoint / OpcUaPoint **不搬**：DbMaintenance 是 Engine 專屬；MqttSetting 三份內容刻意不同（ClientId、retain）；DatabaseSchema 與程式同版號；Modbus / DBPoint / OpcUaPoint 是現場資料且 Web 已直接寫 Engine 資料夾（無複本）
- 升級遷移（Install.bat）：還原現場設定後，對四檔逐一：`Shared\<檔>` 已存在 → 不動；不存在但 Engine 複本存在 → **move** 過去（若 Web 複本與 Engine 複本內容不同，印 `[WARN]` 並把 Web 那份另存 `Shared\<檔>.web-backup` 供人工合併 —— 通知三檔以前 Web 會寫，可能是 Web 那份才是最新）；只有 Web 複本 → move Web 那份；都沒有（全新安裝）→ 寫入包內 `Shared\` 範本（Line 為 placeholder token、Email / Sms 為 example 內容，Engine 視為未設定安全停用）；收尾一律 **del** Engine / Web `App\Setting\` 四檔殘留。Gateway 的 `InstallModbusServer.bat` 只管 dbSetting：偵測同機是否已有 `Shared\`，有就不鋪本機複本，沒有（異機）才從 `dbSetting.example.json` 鋪。詳見 [功能說明書_Release打包與升級.md](功能說明書_Release打包與升級.md) §共用設定檔遷移與回滾
- Web 服務帳號需對 `C:\JOULARIS\Shared\` 有寫入權（預設 LocalSystem 無問題；改受限帳號時要另授權）
- 單元測試 [DbSettingLocatorTests.cs](../ScadaEngine.Tests/Common/DbSettingLocatorTests.cs)、[SharedSettingLocatorTests.cs](../ScadaEngine.Tests/Common/SharedSettingLocatorTests.cs) 鎖住順序（含「Shared 與本機 Setting 同時存在必選 Shared」「生產佈局不會誤判為開發 repo」「Engine / Web 解析到同一份」）；[NotifySettingReloaderTests.cs](../ScadaEngine.Tests/Notification/NotifySettingReloaderTests.cs) 鎖住「只重載對應檔、未知檔名忽略、解析失敗不套用」

## 警報系統

### Alarm MQTT Topic（未恢復警報即時推播）

```
AlarmMonitorService (Engine) 觸發/恢復
    ↓ AlarmMqttPublisher
SCADA/Alarm/Active/{SID}/{type}   QoS=1, Retain=true
    觸發 → 完整 JSON（severity/message/triggerValue/...）
    恢復 → 空 payload（清除 retained）
    ↓ subscribe SCADA/Alarm/Active/+/+
MqttAlarmSubscriberService (Web) → ConcurrentDictionary<"{SID}:{type}", ActiveAlarmItem>
    ↓ GET /Realtime/ActiveAlarms（記憶體讀取）
前端 active-alarm-panel.js（3 秒輪詢）
```

`{type}` ∈ `high` / `low` / `di`，對應 `EventLog.Operator` 2/3/4。Engine 啟動後 republish 一次目前 active 警報以覆蓋舊 retained；Web 啟動時從 `EventLog WHERE ClearedAt IS NULL AND EventType=0` 預填快取。

### 警報規則異動即時生效（控制 Topic）

```
Web AlarmRuleService (儲存 / 刪除規則) → DB AlarmRules
    ↓ AlarmRuleReloadPublisher
SCADA/Sys/AlarmRules/Reload   QoS=1, Retain=false
    payload: { "sid": "{SID}" | null }
    ↓
AlarmRuleReloadSubscriber (Engine BackgroundService)
    ↓ AlarmMonitorService.ReloadAndReevaluateAsync()
    1) ReloadRulesAsync (含孤立警報清掃)
    2) GetLatestDataAsync 取最新值（含計算點，因為 CalculatedPointService 寫入 LatestData）
    3) EvaluateBatchAsync → 觸發 / 恢復 → 寫 EventLog → 發 SCADA/Alarm/Active/...
```

`Sys` 命名空間預留給未來其他系統級控制訊號（避開 `SCADA/Control/#` Modbus 控制 CID 解析路徑）。Retain=false 避免 Engine 重啟時又跑一次最後一筆 reload；Engine 啟動時 `InitializeAsync` 本來就會做完整 reload，不需 retained 補位。`AlarmMonitorService` 內以 `SemaphoreSlim(1,1)` 序列化 reload 避免快取半更新狀態，並保留原 60 秒 Timer 作為 broker 失聯時的退路。

### 前置條件（連鎖遮蔽）與警報延遲

規則可綁「另一點位 X 的條件連續成立 N 秒」才判斷本點警報（閘門 Closed 時清除本點 active 警報），另有本點 on-delay `AlarmDelaySec`。Engine `AlarmMonitorService` 以全點位最新值快取 + **1 秒 tick**（只掃有前置 / 延遲的規則）補判「延遲期滿但值沒變」；ScadaPage 對有前置條件的規則改看實際 active 警報著色。恢復一律 by Operator 清除（不再一恢復清全部類型）；每條規則另可分別設定恢復通知走 Line / Email / 簡訊（`RecoveryNotify*`，一般恢復與前置清除皆適用）。細節 → [功能說明書_Engine核心.md](功能說明書_Engine核心.md) §7.7、[功能說明書_警報設定.md](功能說明書_警報設定.md) §9.4 §9.5。

### 通知通道（Line / Email / 簡訊）

警報觸發與恢復時 `AlarmMonitorService` 依序呼叫三個獨立通道服務（各自 try/catch，失敗不影響警報主流程、不影響彼此）：

| 通道 | 服務 | 路由模型 | 需要網路 |
|---|---|---|---|
| Line | `LineNotificationService` | per-群組 MaxSeverity | 是 |
| Email | `EmailNotificationService` | per-群組 MaxSeverity + 規則綁定（EmailGroupRuleMap） | 是 |
| 簡訊 | `SmsNotificationService` | per-號碼 MaxSeverity | **否**（序列埠簡訊盒 + SIM） |

簡訊通道因序列埠是 Engine 獨占資源，Web 的測試發送/重掃 port 走 MQTT 代理：
`SCADA/Sys/Sms/Cmd`（Web→Engine，Retain=false）與 `SCADA/Sys/Sms/Status`（Engine→Web，Retain=true，含 port/CSQ/SIM/每日額度）。
細節見 [功能說明書_簡訊通知.md](功能說明書_簡訊通知.md)。

三個通道的設定檔（`EmailSetting.json` / `SmsSetting.json` / `LineSetting.json`）在生產機放 `C:\JOULARIS\Shared\`，Engine 讀、Web 讀寫同一份；Web 存檔後發
`SCADA/Sys/Notify/Reload`（Web→Engine，Retain=false，`{"file","requestId"}`）→ Engine 重讀套用 → 回 `SCADA/Sys/Notify/Status`（Engine→Web，Retain=false，`{"file","requestId","success","message","source","path","time"}`），
不重啟 Engine。失敗保留舊設定並寫 EventLog。見 [§共用設定檔解析順序](#共用設定檔解析順序)。

## 用電報表

### 查詢路徑（On-demand 計算）

```
使用者按「查詢」 → /EnergyReport/api/query
    ↓
EnergyReportService.GetReportAsync(circuitId, granularity, start, end)
    1) GetByIdAsync                取迴路
    2) GetLeavesUnderAsync         遞迴展開所有葉子（綁 SID）
    3) BuildBucketRangesAsync      產出 N 個 bucket 的 [起, 訖) 邊界對
         時/日/年 → BuildBoundaries 連續切界（相鄰 bucket 共用邊界點）
         月       → BillingPeriodService 期別切界（每期各自起訖，可能空窗/重疊，不共用邊界點）
    4) for each leaf:
         OUTER APPLY HistoryData WHERE Timestamp <= boundary
           AND Timestamp >= boundary - MaxStalenessHours AND Quality=1   邊界時刻去重後一條 SQL 取值
         每 bucket 訖值減起值 + 套 kWh 溢位規則 → N 個 delta
       各葉子 delta 同位置相加 → 該 bucket kWh
    ↓
EnergyReportResult { buckets[], totalKwh, isHasWarning }
    ↓
Chart.js 長條圖 + 表格；按「匯出 Excel」 → /EnergyReport/api/export → ClosedXML .xlsx
```

階層存於 `EnergyCircuit`（自參照樹，葉子綁 SID + MaxKwh，虛擬節點不綁）。每個節點有 `Sign` 欄位 (±1)，葉子有效權重 = 從查詢根到葉路徑上所有 sign 的乘積（不含查詢根本身），用以表達「總表 − 已分配子表」「A+B+C−D」這類算式；root 強制 +1，bucket 可為負值。溢位規則仍套在葉子原始 delta 上，sign 只在合併時套用。粒度綁固定期間選擇器（時=日、日=月、月=起訖月、年=起訖年），避免任意起訖造成 bucket 邊界語意混亂。**月粒度的「月」= 電費月結期別**（YYYY-MM 為期別編號）：期界由 `BillingPeriodService` 依 `BillingPeriods` 表解析（未自訂 = 級聯推導，完全未自訂 = 自然月），涵蓋用電報表 / 電費報表 / EMS 電費卡；年粒度維持自然年。因月報 on-demand、無月度預聚合表，期別設定改動即時生效、歷史月報自動用新設定重算，不需回填。

**期別共有三種語意，勿混用**（2026-08-05 拆分）：
| 報表 | 月粒度切界 | 來源 |
|---|---|---|
| 用電報表 / 電費報表 / EMS 電費卡 | 電費期別 | `BillingPeriodService` ← `BillingPeriods` |
| 用水報表 / 水費報表 / EMS 水表卡 | **水費期別** | `WaterBillingPeriodService` ← `WaterBillingPeriods` |
| 用氣報表 / 氣費報表 / EMS 氣表卡 | **氣費期別**（可兩月一期） | `GasBillingPeriodService` ← `GasBillingPeriods` |
| 冷凍噸報表 / 空調水系統迴路資訊 / 能源申報 / 能源基線·EnPI | **曆月**（不走任何期別） | 服務內建曆月切界；EMS API 走 `EmsController.ParseCalendarPivot()` |
| 空壓機能源申報（kWh + 產氣量 Nm³） | **曆月**（不走任何期別） | `EnergyReportService.BuildCalendarMonthRanges`（兩側共用，與冰水申報同一支 kWh 方法） |
| 設備效率診斷（冰機 / 空壓機） | **曆月**（不走任何期別） | `EquipmentEfficiencyReportService` 沿用冷凍噸 `BuildBoundaries`；EMS API 走 `EmsController.ParseCalendarPivot()` |

⚠️ 三套期別表結構**不再全等**：`GasBillingPeriods` 比電/水兩套多一個 `IsSkipped bit`，用來把某一期「刪除」以組出**兩月一期**（供氣事業常見抄表週期）。被刪除的期別不產生 bucket，其日數由相鄰期吸收 — 一年月粒度因此只有 6 個 bucket。細節見 §用氣報表與氣費計算。

冷凍噸報表 2026-08-05 起改曆月 — 它綁定能源申報、申報固定曆月，且不是算錢的報表，跟著電費期別走反而與申報數字對不上（⚠️ 行為變更：已自訂電費期別的現場，月數字與此版之前不同）。2026-08-21 新增的 `/ChilledWaterCircuitInfo`（空調水系統迴路資訊，冷凍噸體系的第二個瀏覽入口）沿用同一計算核心與同一曆月語意，兩頁數字必然一致；RT·h 顯示位數全站統一為**小數一位**。能源基線 / EnPI 則是刻意與電費期界脫鉤（見 `EnergyBaselineService`）。HistoryData 是唯一資料來源，**Engine 只做葉子層 hourly 預聚合**（見下節），**sign / 階層 / 虛擬節點加總仍 on-demand 在 Web 端做**，迴路結構改變即時生效不需回填（四個迴路設定頁 + LogicFlow / Designer 樹皆可拖曳搬移，後端 `TreeSortValidator` 驗循環 / 單一根 → [功能說明書_階層樹拖曳搬移.md](功能說明書_階層樹拖曳搬移.md)）。詳細功能說明見 [功能說明書_能源管理.md](功能說明書_能源管理.md)。

### 邊界值 Staleness Window

`EnergyReportService.GetBoundaryValuesAsync` 與 `EnergyLeafAggregator` 取「最近一筆 HistoryData」時加上 `Timestamp >= boundary - MaxStalenessHours` 條件（預設 2 小時，`appsettings.json:EnergyAggregation.MaxStalenessHours` 可調）。超過視窗一律視為 null，避免電表斷線復原時把整段累積差異全壓在恢復首小時的「巨柱」假象。Web 報表端（僅 on-demand 路徑，Engine hourly 預聚合不變）邊界為 null 時再 fallback 取該 bucket **區間內首 / 末筆**有效讀數補位並標 `isPartial`（電表期中上線的月份顯示「自上線起」累計，缺讀數那段不計也不挪到鄰桶），兩邊都補不到才 `isStale` → [功能說明書_能源管理.md](功能說明書_能源管理.md) §Step 3.7。**預聚合與 on-demand 必須讀同一份設定**，保住兩條路徑語意一致 — 不然「當前未完成那小時」（on-demand 算）和「上個小時」（讀 EnergyLeafHourly）會出現數字不連續。

### 葉子層 Hourly 預聚合（Engine）

```
Engine BackgroundService (XX:02 觸發 + 啟動 catch-up)
    ├─ EnergyLeafAggregationService → 每葉子 SID 取 [hourStart, hourStart+1hr) 兩邊界值 → 套溢位 → UPSERT
    └─ EnergyLeafBackfillSubscriber (訂閱 SCADA/Sys/EnergyLeafHourly/Backfill, Retain=false)
         payload { "sid": null | "DB1-S5", "from": "yyyy-MM-dd", "to": "yyyy-MM-dd" }
         按月分批 + 每批 sleep BackfillBatchSleepMs (預設 500ms)
    ↓ UPSERT (MERGE on (SID, HourStart))
EnergyLeafHourly (SID, HourStart, DeltaKwh, Quality, IsRolledOver, CreatedAt)
```

**Sparse storage 三段語意**（與 `EnergyLeafAggregator.ComputeAsync` 一致）：
- **兩邊界都有值** → `Q=1, Delta=計算值（含 MaxKwh 溢位修正）`
- **只缺一邊**（staleness 過期或 SID 剛上線）→ `Q=0, Delta=0`（掉線 transition 標記，留給儀表板畫灰 bar）
- **兩邊都缺** → **不寫該列**（避免長期斷線 SID 灌爆空列；Web 端在記憶體用 dictionary lookup 補 0 即可）

觸發時點 XX:02 是給 DB 來源 polling buffer（避免 XX:00 整點時最末幾筆 HistoryData 還沒寫入）。啟動時做 `CatchUpHours`（預設 24）小時的補算覆蓋週末停機等情境。HourStart 用 local time（與 HistoryData.Timestamp 同基準，不轉 UTC）。Engine 完全不做 sign / 虛擬節點加總，那些仍由 Web on-demand 套用，確保迴路結構改變即時生效。Backfill MQTT 訊號典型用途：首次全量補算（sid=null）、單一 SID 在 MaxKwh 改動後重算歷史。

### 電費計算（Web 端逐時計價）

```
EnergyLeafHourly（Engine XX:02 寫入）
    ↓ Web ElectricityCostAggregationService（XX:05 觸發，每輪 DELETE+INSERT 覆蓋近 48h；啟動 catch-up ElectricityCost:CatchUpDays 天，預設 7）
ElectricityCostHourly (SID, HourStart, Period[PK], Kwh, UnitPrice, Cost, PlanId, PlanType, Season, Quality)
    ↓ 查詢：GetLeavesUnderAsync 遞迴 CTE 取 EffectiveSign，per-SID GROUP BY 後記憶體套 sign（同用電報表模式）
GET /EMS/api/electricity-cost → EMS「電費狀態」卡（本期 = BillingPeriods 期別）
POST /ElectricityCostReport/api/query → 電費報表（bucket 切界沿用用電報表；progressive 期別級距分攤）
```

計算放 Web 不放 Engine — TariffConfig 模型 / TariffSettingService / 重算按鈕都在 Web，同一套邏輯直接重用；輸入純 DB 讀取無即時性需求。**逐日依「採用時間軸」選版計算**（`SystemSettings.electricity_tariff` 的 `adoptions[]`，見下段）。tou 依（DayType × 季節）時段表落段，邊界非整點按分鐘比例分攤拆列（PK 含 Period）；DayType 判定假日優先於星期（`Holidays` 表 → `sun_offday`，由 /HolidaySetting 頁維護）；progressive 只存 kWh、查詢時套級距（避免逐時攤提在重算時的順序相依）。詳見 [功能說明書_電費設定.md](功能說明書_電費設定.md) §電費計算、[功能說明書_國定假日設定.md](功能說明書_國定假日設定.md)、[功能說明書_電費報表.md](功能說明書_電費報表.md)。

**需量費回測分支（契約容量最佳化，2026-10）**：不走 `ElectricityCostHourly`，而是 on-demand 讀 `DemandData` 的整刻樣本（分鐘 ∈ {0,15,30,45} = 台電固定 15 分鐘窗口）→ 每計費月（電費期別）尖峰最高需量 + 窗口完整率 → 套 `electricity_tariff` 的方案單價與 `contracts[]`（契約容量歷史）→ Common `ContractCapacityCalculator` 算保守建議 / 最低成本點 / 平底區間。超約附加費 2 倍 / 3 倍與二段式非夏月門檻（經常 + 非夏月契約）依台電電價表 114/11/17 版。詳見 [功能說明書_契約容量最佳化.md](功能說明書_契約容量最佳化.md)。

**電價方案版本化（採用時間軸）**：`TariffConfig` 分兩層 —— `plans[]` 是**方案目錄**（台電 seed 20 個不同用戶類別 + 使用者自建的 `custom` 類），`adoptions[]` 是**時間軸**（一列 = 從某日起改用某方案）。選版 = 生效日 ≤ 目標日的最新一筆採用紀錄。之所以不照抄水費的「每方案帶生效日」，是因為 seed 的多個類別方案本來就並存、彼此不是版本關係，混在同一條時間軸會選錯。

`ElectricityCostHourly.PlanId` 逐列快照計算當下的方案，報表端 by `PlanId` 反查套級距 → **多版本天然支援，schema 未改**。歷史不被追溯改寫（改費率要主動重算）。舊設定只有 `szActivePlanId` 時，讀取時自動補一筆 `2000-01-01` 生效紀錄（`MigrateLegacyActivePlan`），歷史數字不變。⚠️ 重算時某日查無適用方案 → 該日舊列被 DELETE 且不重寫（刻意：留著舊方案金額等於錯誤數字無聲存活；來源 `EnergyLeafHourly` 未動故可補紀錄後重算還原）。

### ScadaPage 累積量元件（任意 SID 當日/當月累積）

```
ScadaPage 圖面 AI 點位元件（szValueMode = day | month，class scada-rt-acc）
    ↓ 30 秒慢輪詢（與 1 秒即時輪詢分離；換頁立即補打一次）
POST /api/scadapage/accumulation（批次，sid+mode+kind+max 去重，上限 50）
    ↓
WidgetAccumulationService（Scoped）
    ├─ meter     — 現值(MQTT 記憶體快照優先) − 期初邊界值（同 EnergyReport 溢位/staleness 語意）
    └─ integrate — HistoryData 左矩形時間積分（值×Δt 小時，段長 clamp MaxGap 5 分不灌水）
         分層快取 WidgetAccumulationCache（Singleton）：
         L1 完成日 / L2 今日完成小時 bucket 永久快取（跨期 prune）
         L3 當前小時尾段即時算（≤60 筆 PK seek）＋ L4 結果 30s 微快取
```

與 EnergyCircuit 體系互補：EnergyReport 綁迴路樹做報表，此元件吃**任意 SID**（Modbus/DB/OPC UA/CALC）給圖面即看。meter 邊界值與溢位規則沿用 EnergyReport 已驗證語意（複製於 `WidgetAccumulationService`，含註解對照）；integrate 是新語意 — 針對流量（m³/h）、功率（kW）等瞬時值點位積分出量（m³、kWh），單位由使用者在 Designer 屬性面板自訂（`szAccUnit`）。設定於 `appsettings.json:ScadaPageAccumulation`。詳見 [功能說明書_SCADA監控頁.md](功能說明書_SCADA監控頁.md) §7.4 (2)。

**迴路指標元件**（AI 點位/表格 cell 綁 EnergyCircuit）走另一支 `POST /api/scadapage/circuit-metric`（30 秒輪詢、50 筆分批）：`day_kwh`/`month_kwh` 複用 `EnergyReportService.GetBucketKwhForRangesAsync`（曆日/曆月切界），`period_kwh`/`period_cost` 直接取 `ElectricityCostService.GetStatusAsync`（EMS 電費卡同一支，零重算），`WidgetCircuitMetricCache` 60s 結果快取；虛擬迴路（無 SID）也能顯示。詳見 [功能說明書_SCADA監控頁.md](功能說明書_SCADA監控頁.md) §7.4 (2) 迴路指標模式。

### 迴路用電虛擬點位（Engine，NRGD-/NRGM-/NRGP-）

Designer 迴路指標綁 `nCircuitId + szMetric` 走專用 API、不經點位管線，警報引擎（只認 SID）接不到 — 要對「某迴路今日用電超標」設警報，必須造虛擬 SID。`CircuitEnergyVirtualPointService` 比照需量 DMD- 模式：

```
Engine BackgroundService（每 5 分鐘對齊整 5 分）
    ├─ 一次撈 EnergyCircuit 全樹 → 記憶體展開各迴路葉子（有效 sign = 路徑 Sign 乘積，語意同 Web GetLeavesUnderAsync CTE）
    ├─ 讀 BillingPeriods rows → Common BillingPeriodResolver 推導當前期別起日（與 Web 報表同一份邏輯）
    ├─ 每唯一葉子 SID 一次查齊四邊界值（今日 00:00 / 本月 1 日 / 期別起日 / now，OUTER APPLY TOP 1 + staleness）
    └─ 每迴路 Σ(葉子 delta（MaxKwh 溢位）× sign) → 三個虛擬點位三路發布
         NRGD-{circuitId}（每日用電，曆日）/ NRGM-{circuitId}（每月用電，曆月）/ NRGP-{circuitId}（本月電度，電費期別）
         → RealtimeDataStorageService（記憶體+LatestData）/ HistoryDataStorageService / MQTT
```

- **全部迴路**（含虛擬節點）都發布；staleness 沿用 `EnergyAggregation:MaxStalenessHours`（與 hourly 預聚合同一份設定）
- **期別推導單一真相**：`ResolvePeriod`/`ResolveCurrentPeriod` 純邏輯抽至 `ScadaEngine.Common/Data/Services/BillingPeriodResolver.cs`，Web `BillingPeriodService` 改委派（DB 讀寫與快取留 Web）— Engine 不複製推導，改期別設定 5 分鐘內生效
- **Quality 寧缺勿假**：任一葉子邊界缺值（掉線超過 staleness 視窗）或迴路無葉子 → 整迴路發 `值=0, Quality=Bad`，警報引擎既有 Bad 防呆生效不誤觸發
- 跨日/跨月/跨期歸零屬預期行為：前期觸發的上限警報走既有恢復流程（當期事件當期結案）
- Web 警報選點器（AlarmSetting）設備下拉「迴路用電」→ 迴路 → 每日用電/每月用電/本月電度；與 Designer `day_kwh`/`month_kwh`/`period_kwh` 同語意（`period_cost` 電費因電價逐時計價整套在 Web，刻意不做）

## 用水報表與水費計算

> ⚠️ **命名區隔**：本體系全部使用 `WaterMeter*` 前綴（`WaterMeterCircuit` / `WaterMeterLeafHourly` / `/WaterMeterSetting`…），處理**累積式水表**（讀數單調遞增的 m³ / L 水量表）。既有 `WaterCircuit` / `WaterLeafHourly` / `/ChilledWaterSystem` / `/ChilledWaterCircuitInfo` 是**空調水系統冷凍噸**（RT 瞬時值 AVG×1h 積分，負 RT 樣本逐筆當 0 再平均），兩者演算法與領域完全不同，互不相干。

### 資料流

```
水表點位（Modbus / Calculated / DB，累積讀數 m³ 或 L）
    ↓ HistoryData（與電表同管線）
Engine WaterMeterLeafAggregationService（XX:02 觸發 + 啟動 catch-up WaterMeterAggregation:CatchUpHours，預設 24）
    │  WaterMeterLeafAggregator：每葉子 SID 取 [hourStart, +1hr) 兩邊界值（staleness window 同電表，
    │  WaterMeterAggregation:MaxStalenessHours 預設 2）→ 原始單位相減 + MaxVolume 溢位 → × UnitScale 換算 m³
    ↓ UPSERT (MERGE on (SID, HourStart))
WaterMeterLeafHourly (SID, HourStart, DeltaM3, Quality, IsRolledOver, CreatedAt)
    ↓ Web WaterUsageReportService：per-bucket SUM(DeltaM3 × EffectiveSign)（sign / 階層 / 虛擬節點 on-demand）
POST /WaterUsageReport/api/query → 用水報表（月粒度走 WaterBillingPeriods 水費期別）
GET  /EMS/api/water-usage / water-breakdown / water-cost → EMS 三張水表卡
POST /WaterCostReport/api/query → 水費報表
```

Sparse storage 三段語意與電表 `EnergyLeafAggregator` 完全一致（兩邊有 Q=1、缺一邊 Q=0 Delta=0、兩缺不寫列）。與電表的差異只有兩點：**MaxVolume**（以點位原始單位計的溢位上限）與 **UnitScale**（綁定時依點位單位定案的 m³ 換算係數，m³ 系=1、L 系=0.001，之後改點位單位字串不追溯改義）。單位關鍵字對照表在 `WaterMeterCircuitService.ResolveUnitScale`（「度」刻意不納入，避免與電度混淆）。

用水報表與電費報表不同 — **直接加總 `WaterMeterLeafHourly`**，不再回頭查 HistoryData（電表報表因需任意 bucket 邊界而查 HistoryData；水表 bucket 均對齊整點，預聚合表即夠）。

### 水費（台水流動水費，on-demand）

只做**流動水費**分段累進（1 度 = 1 m³；不做基本費/TOU/季節）。**刻意不建 `WaterCostHourly`、不做逐時背景服務** — 水費 = f(期別總量)，逐時成本無意義；報表/卡片當下由 `WaterMeterLeafHourly` 加總期別用水量再套級距。

- 費率存 `SystemSettings.water_tariff`（整份 JSON），seed `ScadaEngine.Web/Setting/water-tariff-taiwater-defaults.json`（台水四級距：1–10 度 7.35、11–30 度 9.45、31–50 度 11.55、51 度以上 12.075 元/度）
- **方案含生效日**：計算某期水費時依「期別起日」選用當時生效的方案版本（`WaterTariffService.SelectPlanForDate`），改費率不會追溯改寫歷史水費
- 計費週期走 **`WaterBillingPeriods` 水費期別**（`WaterBillingPeriodService`，`/WaterBillingPeriodSetting` 維護）。**與電費期別完全獨立** — 台水與台電抄表日不同，兩套各自設定互不影響；每迴路獨立對自身期別總量套級距（無占比分攤）
- 無主水表（IsMainMeter）概念 — EMS 卡片「全廠用水」= 樹根節點加總

Web 服務：`WaterMeterCircuitService`（迴路樹 CRUD）/ `WaterUsageReportService` / `WaterTariffService` / `WaterCostService`（級距純邏輯 `ApplyTiers` 有單元測試鎖規則，`ScadaEngine.Tests/WaterMeter/`）。詳見 [功能說明書_用水報表.md](功能說明書_用水報表.md)、[功能說明書_水費設定.md](功能說明書_水費設定.md)。

## 用氣報表與氣費計算

> ⚠️ **命名區隔**：本體系全部使用 `GasMeter*` 前綴（`GasMeterCircuit` / `GasMeterLeafHourly` / `/GasMeterSetting`…），處理**累積式天然氣表**（讀數單調遞增的 m³ / Nm³ / 度 氣量表）。刻意**不用** `GasCircuit` — 專案已有 `WaterCircuit`（冷凍噸）與 `WaterMeterCircuit`（水表）兩套易混名稱，避免產生第三組。

氣與水在物理與資料特性上同構（都是累積式讀數、都以 m³ 計量、成本都是「期別總量 → 分段累進」），故**平行複製一套 `GasMeter*`，不抽共用泛型「累積式計量」層** — 維持專案既有的三套平行樹慣例（`EnergyCircuit` / `WaterMeterCircuit` / `WaterCircuit`），且各自獨立 → 改氣費邏輯永遠不可能弄壞水費。

### 資料流

```
氣表點位（Modbus / Calculated / DB，累積讀數 m³ / Nm³ / 度 / L）
    ↓ HistoryData（與電/水表同管線）
Engine GasMeterLeafAggregationService（XX:03 觸發 + 啟動 catch-up GasMeterAggregation:CatchUpHours，預設 24）
    │  GasMeterLeafAggregator：每葉子 SID 取 [hourStart, +1hr) 兩邊界值（staleness window
    │  GasMeterAggregation:MaxStalenessHours 預設 2）→ 原始單位相減 + MaxVolume 溢位 → × UnitScale 換算 m³
    ↓ UPSERT (MERGE on (SID, HourStart))
GasMeterLeafHourly (SID, HourStart, DeltaM3, Quality, IsRolledOver, CreatedAt)
    ↓ Web GasUsageReportService：per-bucket SUM(DeltaM3 × EffectiveSign)（sign / 階層 / 虛擬節點 on-demand）
POST /GasUsageReport/api/query → 用氣報表（月粒度走 GasBillingPeriods 氣費期別，已刪除期別不產生 bucket）
GET  /EMS/api/gas-usage / gas-breakdown / gas-cost → EMS 三張氣表卡
POST /GasCostReport/api/query → 氣費報表
```

演算法與 `WaterMeterLeafAggregator` **完全對稱**（sparse storage 三段語意、MaxVolume 溢位、UnitScale 換算），差異只有三處：

1. **觸發時點 XX:03**（電表 XX:02 / 水表 XX:02 / 氣表 XX:03，錯開避免同時掃 `HistoryData` 邊界值）
2. **點位判定改為「單位 + 名稱」雙條件**（`GasMeterCircuitService.ResolveGasPointScale`，下拉過濾與存檔驗證共用同一支）：
   - **單位可換算 m³**：`m³ / m3 / Nm³ / Nm3 / SCM / CMD / CMS / 立方公尺 / 立方米 / 米立方` → 1、**`度` / `氣度` / `天然氣度` / `瓦斯度` → 1**（天然氣帳單 1 度 = 1 m³）、`L / liter / litre / 公升 / 升` → 0.001
   - **且** 點位**名稱**含天然氣關鍵字（`天然氣 / 瓦斯 / 燃氣 / 用氣 / 氣量 / 氣表 / 氣度 / gas / LNG / CNG / LPG`…）**或** 單位本身已無歧義（`Nm³ / SCM / 氣度 / 天然氣度 / 瓦斯度`）

   ⚠️ **單位對照表納入「度」與水表刻意相反**（水表排除「度」是為避開電度混淆）。只看單位會把**電表 kWh 點位**撈進氣表下拉 → 綁錯就是拿電度數算氣費；單位字串無從分辨電度與氣度，**點位名稱才是唯一可靠訊號**，故加上名稱條件（順帶也排除同為 m³/L 的水表點位）。關鍵字刻意不收單一個「氣」字（誤中空氣/氣壓/冷氣）與 `NG`（No Good）。
   由 `ScadaEngine.Tests/GasMeter/ResolveGasUnitScaleTests.cs` 鎖住（含「度」在兩套對照表回不同值、以及「電表點位單位標度但名稱無氣關鍵字 → 排除」的斷言），避免日後被「統一」。
3. **氣費期別可兩月一期**（見下節）

### 氣費期別的 IsSkipped（兩月一期）

`GasBillingPeriods` 比電/水兩套多一個 `IsSkipped bit`。`GasBillingPeriodService` 的解析分兩層：

- **nominal**：等同水費版級聯推導，skipped row 視同不存在
- **effective**：skipped 期回 null；存在的期別**向後吸收**同年緊接其後的連續 skipped 期；本期之前同年皆 skipped 時**向前吸收**至該年 1 月起始

→ 「刪除某期 = 其日數併入前一期」「刪除該年第一期 = 由下一期向前吸收」皆由推導自然得出，
**刪除 / 復原都只寫或刪單一 row、不動鄰期，完全可逆**。刪掉 2/4/6/8/10/12 月即得全年 6 期（日數合計仍 365/366、無空窗無重疊）。

⚠️ `GasBillingPeriodService` 因此**不再與電/水兩版結構全等** — 日後勿「照水版對稱修正」而移除 skipped 分支，否則兩月一期直接失效。規則由 `ScadaEngine.Tests/GasMeter/GasBillingPeriodServiceTests.cs` 鎖住。

### 氣費（天然氣流動氣費，on-demand）

只做**流動氣費**分段累進（1 度 = 1 m³；不做基本費/TOU/季節/熱值換算）。**刻意不建 `GasCostHourly`、不做逐時背景服務** — 同水費，成本 = f(期別總量)。

- 費率存 `SystemSettings.gas_tariff`（整份 JSON），seed `ScadaEngine.Web/Setting/gas-tariff-defaults.json`。
  **天然氣無全國統一費率**（依供氣事業合約），seed 刻意是**空白單一級距範本（1 度以上、單價 0）**，由使用者照帳單填入。
- **方案含生效日**：依「期別起日」選版（`GasTariffService.SelectPlanForDate`），改費率不追溯改寫歷史氣費
- **級距與期別長度完全解耦**：期別設兩月一期時，使用者在費率頁直接填「一期」的級距數字，系統**不做任何倍率換算**，費率方案也不含「期別月數」欄位（能靠輸入直接表達的，不做機制）
- 無主氣表概念 — EMS 卡片「全廠用氣」= 樹根節點加總

Web 服務：`GasMeterCircuitService`（迴路樹 CRUD）/ `GasBillingPeriodService`（含 IsSkipped 推導）/ `GasUsageReportService` / `GasTariffService` / `GasCostService`（純邏輯 `ApplyTiers` / `ResolveEffective` / `ValidatePlan` 皆有單元測試鎖規則，`ScadaEngine.Tests/GasMeter/`）。詳見 [功能說明書_用氣報表.md](功能說明書_用氣報表.md)、[功能說明書_氣費設定.md](功能說明書_氣費設定.md)。

效率 = 產出 ÷ 投入；兩類設備只差角色清單 / 指標公式 / 門檻，其餘全部共用（以 `Kind` 區分）。

點位（/Designer/Points + Device 分群）
    ↓ 設定頁前端掃描（js/equipment-scan.js 純函式：resolveEquipRole + 中文別名包含式）→ 使用者勾選 / 手動補
EquipmentProfile + EquipmentPointBinding（Scale 由伺服端依單位重算）
    ├─ Web 即時：MqttRealtimeSubscriberService 快取 × Scale → EquipmentMetricCalculator → /EMS/api/equipment/realtime
    └─ Engine EquipmentHourlyAggregationService（XX:06 + catch-up；每次觸發重讀設定 → 免重啟）

## 能源日報

每日 **02:00** 由 Web 端 `DailyReportSchedulerService`（BackgroundService，30 秒輪詢 + 去重旗標，骨架同 `ElectricityCostAggregationService`）生成**前一日**日報快照並依設定寄送 HTML Email。放 Web 端的理由：四報表服務 / 假日 / 天氣 / EventLog / MailKit 全在 Web，放 Engine 要重複實作全部報表邏輯。

```
02:00 觸發（在 Engine XX:03 水/氣 Hourly 聚合完成之後，前一日 23 時資料已齊）
  DailyReportService.BuildAsync(前一日)
    ├─ EventLog 警報摘要（EventType 0+1：發生/恢復/未確認 + 明細，訊息經 AlarmMessageLocalizer 以全局語言渲染）
    ├─ 四能源別 24 小時序列 + 日總量 — 各體系「root 迴路合計」（多 root 加總；無迴路 → isAvailable=false 區塊隱藏）
    │    電 EnergyReportService / 水 WaterUsageReportService / 氣 GasUsageReportService / RTh RefrigerationTonReportService
    ├─ 五組比較區間：[D] [D-1] [D-7] [本月1日~D] [去年同月1日~同日數(min 處理 2/29)]
    │    → 單日比較（前日/上週同星期）+ MTD 年同期比較 + kWh/RTh 效率比值
    ├─ 假日旗標（Holidays 表：D / D-1 / D-7）+ 外氣日均溫（Weather S1 對 HistoryData AVG，未設定自動略過）
    └─ DailyReportInsightService.EvaluateRules（規則式，不串 LLM API）
         假日效應（IsHolidayHintEnabled=0 整類跳過）/ 溫差>3°C / 警報關聯 / 效率偏離 / 中性 fallback
  → 序列化 JSON 存 DailyReportSnapshot（UPSERT by ReportDate）
  → IsMailEnabled 時 DailyReportMailService 逐收件人寄送（DailyReportHtmlBuilder 產 inline-style HTML，
     純 CSS bar 不產圖片；警報僅前 20 筆），結果寫 EventLog（EventType=3 + NotifyChannel='Email'，格式同 NotifyDeliveryLogger）
     並回寫 MailStatus（冪等：1/3 不重寄、2 不自動重試）
```

- **快照 = 唯一真相**：Email 與 Web 頁讀同一份 PayloadJson，歷史日報不受資料回補影響；區塊顯示由 `SectionFlags` 於**顯示端**過濾（快照永遠存全部區塊，改設定即時生效不需重生成）
- **catch-up**：Web 啟動時最近 N 天（`DailyReport:CatchUpDays`，預設 3）缺快照就補生成，**補生成不補寄**（昨日除外 — 主迴圈當日觸發含補寄，Web 重啟漏跑 02:00 仍會寄）
- **語言**：`DailyReportSetting.Language` 全局單選（zh-TW/en），提示文字與警報訊息於生成時以該語言渲染進快照；文案模板在 `Resources/Services.DailyReport{InsightService,HtmlBuilder}.{,en}.resx`
- Web 頁 `/DailyReport`：選日期瀏覽任一天（有快照讀快照，無快照即時計算不落 DB、標「即時計算」徽章）；警報明細預設收合前 20 筆可展開
- 設定頁 `/DailyReportSetting`：寄送開關 / 語言 / 門檻（預設 ±15%）/ 假日提示開關 / 區塊勾選 / 收件清單 / 測試寄送（【測試】主旨，全域 throttle）

## 演算法 status 協定

LogicFlow `algorithm` 節點呼叫 Python `/algorithms/{name}/evaluate` 或 in-process C# 演算法時，回傳結構化 StatusCode：

```
result (dict<str,double>)        — 輸出值
statusCodeId / statusCodeName    — 例 10 / "DIVIDE_BY_ZERO"（merged，取 perOutput 中 severity 最高者）
severity                         — Info / Warning / Error
perOutput (dict<port,status>)    — 每個 output port (含 variadic suffix) 的 status
```

`Error` severity 走 **per-output port** 判斷：`LogicFlowExecutionService.HasUpstreamBad` 對 algorithm 節點依消費邊線的 `sourcePort` 查 `AlgoPerOutputStatus[sourcePort]`，**僅該 port 下游**節點不再評估、輸出節點本輪跳過不寫 Modbus；同節點其他 OK port 下游正常傳值。`Warning` / `Info` 仍傳遞結果，僅 UI 邊線反灰 + tooltip。

每個 output port 各自跑「OK ↔ 非 OK」切換偵測寫 EventLog，SID 格式 `ALGO:{nodeId}@{treeId}:{outputKey}`，Severity ≥ Warning 才寫（Info / WARMUP 不寫，避免雜訊）。混合狀態（cop1 Error / cop2 OK）會分兩條時序線記錄，不被 merged 掩蓋。

Python helper：`from _status import AlgoStatus, make_status, make_result`（`_*.py` 不會被當演算法載入）。
C# helper：`using ScadaEngine.Algorithms;`（`_*.cs` 不會被當演算法編譯，而是當共用 SyntaxTree 加入每個演算法的編譯，每個 algo 透過 `AlgorithmResult.Ok(...)` / `AlgorithmResult.From(..., AlgorithmStatusCode.DivideByZero)` 回傳）。

對照表單一來源：[功能說明書_演算法服務.md](功能說明書_演算法服務.md)。

## LogicFlow 歷史值讀取

讀取點位（input）與 A/B 接點（contact_no / contact_nc **點位模式**）可勾選「讀取歷史值」，改讀「now − N 分鐘」的 `HistoryData` 值（N = 1–43200，上限 30 天，受 HistoryData 保留期限制）。**預設不勾**：序列化 JSON 不帶新欄位（`histEnabled` / `histOffsetMinutes`），Engine 與前端行為與即時值完全相同（向後相容）。解析度天然為 **1 分鐘**（HistoryDataStorageService 每分鐘存一筆）。

### 資料流（Engine 執行端）

```
HistoryData（每分鐘一筆）
    ↓ 每 1 分鐘：RefreshHistoryCacheAsync()
    │   掃全部 diagrams 收集啟用組合 (SID, offsetMinutes)（Distinct）
    │   每組 GetHistoryTableDataAsync(sid, target−5min, target) 取 ≤ target 最近一筆 Quality=1
    ↓
_historyCache（key=(SID, offset)，snapshot swap，照 _latestCache 模式）
    ↓ 主迴圈（200ms）同步讀快取，不打 DB
四處讀值路徑：GetNodeOutputValue / EvalContact 點位模式 / HasUpstreamBad / HasUpstreamBadFromSource
```

- **查無值（目標時間 ±5 分鐘窗內無 Quality=1）→ 該節點視為 Bad**：走既有 Bad 傳遞語意，下游節點不評估、Output 不寫入。新點或剛上線未滿 offset 時長、HistoryData 已過保留期 → 一律 Bad，屬預期行為。
- DB 每分鐘查詢次數 = 不同 (SID, offset) 組合數；`HistoryData` PK = SID+Timestamp，5 分鐘窗點查走 PK。
- Engine 重啟後歷史讀取立即可用（資料在 DB，首輪 `RefreshCachesAsync` 即刷新，無暖機空窗）。

### 前端（編輯器 + 預覽）

- 點位選擇對話框（picker.js）：checkbox「讀取歷史值」＋「N 分鐘前」數字欄，僅 input / contact 顯示（output、排程模式不顯示）；切排程或非點位節點類型時自動清除欄位。
- 畫布 badge：啟用節點顯示「⏱ -N分」（render.js `histBadgeHtml`，i18n key `logicflow.hist.badge`）。
- 瀏覽器預覽（eval.js）：呼叫 `GET /LogicFlow/api/history-value?sid=&offsetMinutes=`（LogicFlowService 同 Engine 規則查詢），結果依 (SID, offset, 分鐘) 快取於 `S._histCache`，每分鐘最多查一次；查不到 → 節點 `_isBad`、值顯示 `--`。

## HASP 授權守衛（LicenseBridge）

**目的**：以 HASP（Aladdin/Sentinel）USB 加密狗做軟體授權，未插狗 / 授權碼不符 → 停止 Modbus 採集。

**為何拆成獨立專案**：`Aladdin.HASP` 執行庫需 **.NET Framework 4.8（32-bit）**，Engine 是 .NET 8 → 用 bridge 行程隔開執行環境，兩者靠 **Named Pipe** 溝通。`ScadaEngine.LicenseBridge` 專案多目標建置 net48 + net8.0，部署走 net48 版。

```
ScadaEngine.LicenseBridge（Windows Service，服務名 JoularisLicense）
    ├─ NamedPipeServer "ScadaEngineLicense"，收到文字指令 "verify"
    └─ HaspVerificationService.VerifyHasp()：
        hasp.Login(VENDOR_CODE) → GetFile(ReadWrite).Read(48 bytes)
        比對前 20 bytes == "ITRIGELD400B64308309" → 回 "ok" / "fail:{原因}"
        （TerminalServiceDetected / RDP 目前暫時直接放行 — 見程式 TODO）
        ↑ pipe
ScadaEngine.Engine / LicenseService（BackgroundService）
    啟動延遲 5 秒 → 立即驗，之後每 30 分鐘重驗
    ├─ 驗失敗 → 暫停 ModbusCollectionManager 採集 + 更新 LicenseState
    ├─ 驗恢復 → 恢復採集
    └─ 結果以 Retain MQTT 發布至 SCADA/Sys/License/Status
```

- Bridge 執行檔路徑由 Engine 以執行檔目錄相對推算：`<Engine\App>\..\..\LicenseBridge\ScadaEngine.LicenseBridge.exe`（生產機 = `C:\JOULARIS\LicenseBridge\`；`LicenseService.ResolveBridgeExePath`，啟動 log 印出解析結果）。26.6.0 前為寫死 `C:\SCADA\...`。
- Pipe 名 `ScadaEngineLicense`（`LicenseService.PIPE_NAME`，內部協定不隨改名動）；服務名 `JoularisLicense`（`BRIDGE_SVC`，v26.1.0 起；Engine 自救建服務也用此名）。
- Log：`{BaseDir}/Log/bridge-{date}.log`（Serilog，保留 7 天）。
- 相關檔案：[`LicenseService.cs`](../ScadaEngine.Engine/Services/LicenseService.cs)、[`HaspVerificationService.cs`](../ScadaEngine.LicenseBridge/Services/HaspVerificationService.cs)。

**部署**（2026-09 起）：`BuildRelease.ps1` 會 build net48 bridge 打進 release 包 `LicenseBridge\App\`（含 HASP runtime dll，無需外網 / 無需目標機裝 dotnet，靠系統內建 .NET Framework 4.8），`Install.bat` 自動 `xcopy` 到 `C:\JOULARIS\LicenseBridge\` 並建 `JoularisLicense` 服務。**唯二仍需人工**：目標機插上 HASP USB 加密狗、必要時裝 Sentinel/HASP runtime 驅動（`haspdinst.exe -i`，離線安裝）。`Install.bat` 收尾會 `sc query` 印出三個服務（Engine / Web / License）的 RUNNING/STOPPED 狀態。

**.NET Framework 4.8 前置檢查**（Install.bat 開頭）：Engine/Web/ModbusServer 是 self-contained .NET 8 自帶 runtime，唯獨 net48 bridge 靠系統內建 4.8。故 `Install.bat` 在管理員檢查後、任何動作**之前**先讀 registry `HKLM\...\NDP\v4\Full` 的 `Release`（≥ 528040 = 4.8），**缺就印指引並 `exit /b 1` 中止、機器完全不動**（讓現場先裝 4.8＋重開機再重跑）。4.8 是 ~120MB MS redistributable、不能 xcopy，刻意**只偵測不打包**（Server 2016/2019、舊版 Win10 出廠無 4.8，須自行離線補裝：<https://dotnet.microsoft.com/download/dotnet-framework/net48>）。
