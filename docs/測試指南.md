# 自動化測試指南

> 目的：把「AI / 原作者腦中的隱性規則」固化成會自動執行的斷言，讓任何工程師（配任何 AI 或不配）都能安心改動。這是「Claude 沒了怎麼辦」與「工程師離職了怎麼辦」的共同解法。

## 一鍵執行

```powershell
dotnet test                                   # 跑全部
dotnet test ScadaEngine.Tests                 # 只跑測試專案
dotnet test --filter "ResolveDayType"         # 跑特定類別/方法
```

綠燈 = 沒事，紅燈 = 你（或某個 AI）改壞了某條規則。**commit 前務必全綠。**

## 什麼該測、什麼不該測（第一性原理）

判準只有一句：**「這段若被人默默改壞，會不會出事、且沒人會馬上發現？」**

| 該補測試（會出事又難察覺） | 免測（改錯了肉眼馬上看到） |
|---|---|
| 電費 TOU 分段、尖離峰判定 | 按鈕顏色、CSS 間距 |
| 需量 15 分鐘滑動視窗 | 文案、i18n 字串 |
| 能源基線回歸公式 | Razor View 排版 |
| 設備效率公式（kW/RT、比功率、流量 + ΔT → RT、能量加權期間效率）— `ScadaEngine.Tests/Equipment/` | 卡片評級顏色 |
| LogicFlow 演算法節點回傳值 | 純顯示格式微調 |
| Dapper SQL 欄位 alias 映射、關鍵資料轉換 | — |

無腦全補是浪費；該補的漏掉才是風險。

## 測試金字塔（依 CP 值）

1. **單元測試（主戰場）** — 純計算邏輯，不碰 DB / 網路，毫秒級。優先且大量。
2. **整合測試** — 真接一個測試 DB 驗 SQL / 觸發流程。中量。
3. **E2E（Playwright）** — 開瀏覽器點關鍵路徑。少量、只保關鍵。

## 怎麼寫一個單元測試（AAA 骨架）

範例見 [ScadaEngine.Tests/Electricity/ResolveDayTypeTests.cs](../ScadaEngine.Tests/Electricity/ResolveDayTypeTests.cs)。每個測試三段：

```csharp
[Fact]                              // 單一案例；多組資料用 [Theory] + [InlineData]
public void 國定假日_即使平日也判為假日型()
{
    // Arrange：準備輸入
    var dtDay = new DateTime(2026, 2, 17);
    var holidays = new HashSet<DateTime> { new(2026, 2, 17) };

    // Act：呼叫被測方法
    var szResult = ElectricityCostService.ResolveDayType(dtDay, holidays);

    // Assert：斷言期望值，錯了就紅燈
    Assert.Equal("sun_offday", szResult);
}
```

**要點**
- 測試方法名用中文描述「情境_期望」，紅燈時一眼看懂壞在哪。
- 記得測**邊界**（區間頭尾、跨午夜、跨年、空字串、壞輸入）——bug 幾乎都藏在邊界。
- 一個測試只驗一件事。

## 想測 private 方法怎麼辦

優先把「值得測的純邏輯」重構成 `public static`（或 `internal` + `[InternalsVisibleTo("ScadaEngine.Tests")]`），或抽成獨立無狀態的 `*Calculator` 類別。**這一步同時讓正式程式碼更乾淨**——是好事，不是妥協。

## 技術棧

- 框架：**xUnit**
- 斷言：**xUnit 內建 `Assert`**（刻意不引入 FluentAssertions：其 v8 已改商業授權，商用產品有法務風險）
- 假物件（整合測試會用到）：Moq 或 NSubstitute
- **平台相依測試**：斷言 Windows 路徑語意（磁碟機代號、反斜線）的測試改用 `[WindowsOnlyFact]` / `[WindowsOnlyTheory]`（`ScadaEngine.Tests/Common/WindowsOnlyAttributes.cs`），非 Windows 平台自動 Skip 而非紅燈 — macOS 開發機（BuildRelease.command）也能讓 Stop hook 的 `dotnet test` 全綠

## 工作流：測試 = 完成的定義

改動核心邏輯時，「做完」的定義多一條：**有對應測試 + `dotnet test` 全綠才算做完。**
plan 模板 [docs/plans/_template.md](plans/_template.md) 的「測試策略」段會強制你每次回答一次「這次該不該補」，避免憑感覺。

### 自動化：三層安全網

| 層 | 誰被強制 | 狀態 |
|---|---|---|
| ① Claude Code Stop hook | AI 收尾時自動跑 | ✅ **已啟用** |
| ② Git pre-push hook | 任何人 push 前 | ⬜ 未設 |
| ③ CI（GitHub Actions） | 伺服器端 push/PR | ⬜ 未設 |

**① 已啟用**：`.claude/settings.json` 的 Stop hook → [`.claude/hooks/dotnet-test-if-cs-changed.sh`](../.claude/hooks/dotnet-test-if-cs-changed.sh)。
Claude Code 每次收尾時，若工作區有未提交的 `.cs` 變更就自動跑 `dotnet test`；**紅燈會擋下收尾並把錯誤餵回 AI 當場修**，綠燈或沒動 `.cs` 則靜默放行。

> ⚠️ 這層只在「用 Claude Code 開發」時生效。要涵蓋「工程師手動改壞硬推」，需再加第②層 git pre-push hook；要防前兩層被 `--no-verify` 繞過，再加第③層 CI。兩者尚未設定。
